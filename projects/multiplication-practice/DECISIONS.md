## 2026-10-18 — Рішення власника для MVP (D1–D7)
Контракт: `docs/API_CONTRACT.md` і `contracts/api.ts` у гілці `claude/api-contract` (PARTIAL: не злито, виконавці ще не підтвердили).
- **D1 (active, варіант B, підтверджено власником):** логін учня — 3–4 латинські літери (система генерує 4); пароль — 2 літери + 4 цифри, видаються системою. Алфавіт без `i`, `l`, `o` (23 літери): 23²×10⁴ = 5 290 000 комбінацій (обчислено). Окремої функції входу учня НЕ буде: учень входить через Supabase Auth, синтетичний email `<логін>@<STUDENT_EMAIL_DOMAIN>`. **Залишкова слабкість:** блокування спроб у MVP немає; за документацією Supabase ліміт токен-ендпоінта 150 запитів за 5 хв на IP, тож підбір пароля одного акаунта лишається теоретично можливим (потребує довгого часу, але не неможливий). Не перевірено на проєкті: чи приймає Auth 6-символьний пароль; чи приймає домен `.invalid`; чи не обходить вимкнена реєстрація створення користувача адміністратором.
- **D2 (active):** підтримуються типи питань: `true_false`, `single_choice` (4–5 варіантів), `multiple_choice` (3–8), `ordering` (3–8), `matching` (2–8 пар), `numeric`, `short_answer`. VERIFIED: типів `ordering` і `matching` у БД ще немає (enum `question_type`), потрібна окрема міграція. Окремий банк питань для повторного використання — після MVP (підтверджено власником).
- **D3 (active):** публікація тесту лише через серверну функцію, яка перевіряє ключі відповіді; прямі зміни статусу на `published` з клієнта заборонити.
- **D4 (active):** у MVP учень належить одному класу; кілька класів — після MVP.
- **D5 (active):** режим `graded` — без підказок до завершення; режим `practice` — показ правильності після кожної відповіді.
- **D6 (active):** хостинг — спочатку перевірити GitHub Pages разом з Auth; до перевірки не обіцяти.
- **D7 (active — запрошення, схему підтверджено власником):** публічну реєстрацію вимкнути; акаунти вчителів створює власник у панелі Supabase без листів (за документацією, вбудована пошта — 2 листи на годину); `provision-teacher` створює профіль лише для акаунтів із приватного списку дозволених. Те, що вимкнення реєстрації не заважає створенню користувачів адміністратором, потрібно перевірити.
- **Q4 (оцінювання, пропозиція координатора; власник питав, чи достатньо — відповіді ще не отримано):** у MVP для `multiple_choice`, `ordering`, `matching` — «все або нічого» (`checker_version=1`). Часткові бали — `checker_version=2` без зміни схеми, після MVP.

## 2026-10-19 — Без фінансових витрат (active, рішення власника)
**Рішення:** план роботи не передбачає платних послуг. Платні Supabase branches не використовувати; міграції й RLS перевіряти локально (`supabase start` у CI). Платні функції не вмикати, без власного SMTP.
**Не перевірено:** безкоштовність GitHub Actions для цього репозиторію (очікується для публічного репо — звірити з умовами GitHub); ліміти й пауза проєкту Supabase Free; чи доступні на Free налаштування мінімальної довжини пароля й вимкнення реєстрації.
**Статус:** active.
 й версії міграцій (запропоновано, чекає схвалення власника)
**Пропозиція:** (1) версії файлів у `supabase/migrations/` дорівнюють версіям, застосованим у проєкті; (2) права `anon`/`authenticated` на таблиці `public` видаються явно й мінімально, без успадкованих за замовчуванням; (3) спільні конфігурації множення змінюються лише міграцією або серверною функцією, а не клієнтом вчителя; (4) шаблон створюється лише як `draft`.
**Реалізація:** гілка `claude/harden-grants-and-align-migrations` у `teachersergiy-wq/multiplication-practice`; міграція не застосована.
**Рішення власника (D3):** публікація тесту (`draft` → `published`) виконується лише серверною функцією, яка перевіряє наявність ключів відповіді для кожного питання. Зараз клієнт може виставити `published` напряму; це має закрити Grok у межах завдань хвилі 2.
**Статус:** proposed.

## 2026-10-24 — D9: часткові бали для багатокомпонентних типів
**Рішення (власник, варіант B):** `multiple_choice` f = max(0, (правильні − хибні)/n), `ordering` f = частка елементів на своїх позиціях, `matching` f = правильні пари/усі пари; `awarded = round(points × f, 2)`; `is_correct` лише при f = 1, будь-яке f < 1 рахується помилкою. `true_false`, `single_choice`, `numeric`, `short_answer` — «все або нічого». Ключі трьох типів (наявні й нові) мають `checker_version = 2`; завершені спроби не переоцінюються. У `graded` правильність не видається до завершення. Правила — `docs/API_CONTRACT.md` розділ 5.
**Статус:** VERIFIED у базі 2026-10-25 (G6c+G8 застосовано, PR #69; C10 у PR #64). Специфікацію з PR #63 (сусідні пари, наявні ключі v1) відхилено як дублікат.

## 2026-10-25 — D10: генератор тестів множення
**Рішення (власник):** окремі конфіги рівнів 1–5 для 5–9 класів і оновлення 3 класу за файлом власника; прохідний відсоток суворіший з віком (не вище 98%); різні діапазони множників за рівнями; для класів без конфіга береться найближчий нижчий; 5 клас рівень 1 мін. множник 1 (у базі min_factor ≥ 1). Якщо пар бракує, додаються квадрати 11×11 і 12×12. «Супер рівень» (безкінечний до першої помилки, пари таблиці ділення, 7 с мінус 0,5 с кожні 5 питань) — окремий проєкт після генератора.
**Статус:** контракт злито (#71); реалізація PLANNED (G9 #72, C11 #73).
