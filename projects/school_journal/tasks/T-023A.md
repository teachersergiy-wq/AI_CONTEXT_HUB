## Context — Claude's review of 2026-11-02
Verified against the live catalogs of project `dtpyvyedcptdkdsowmco` (read-only queries):
1. Any authenticated user can UPDATE their own `profiles.role`: policy `profiles_update_own_or_owner` has no WITH CHECK, `authenticated` has column UPDATE on `role`, and the only trigger is `updated_at`. This allows self-promotion to `owner`.
2. `anon` has SELECT and INSERT table privileges on all 11 `public` tables and on `v_lesson_window` (broad default privileges). The contract says anonymous access is forbidden.
3. All 32 RLS policies target `{public}`, not `authenticated`.
4. SECURITY DEFINER functions callable by `anon` and `authenticated` through the API: `current_app_role()`, `is_class_teacher(uuid)`, `is_journal_teacher(uuid)`, `handle_new_user()`.
5. `set_updated_at()` has a mutable `search_path`.
6. Auth leaked-password protection is disabled. It may be unavailable on the Free plan: check and report, do not pay for it.

## Scope decisions
- Only the owner has an account now, but the system must stay **ready for several teachers**: keep the owner and teacher policies and the `teacher` role. Do not delete them.
- The repository is public and the site will be public: the Supabase URL and anon key are visible by design, so everything depends on RLS, disabled signup (T-007) and this migration.

## Required
A. **Privileges.** Revoke all privileges on `public` tables, views, sequences and functions from `anon` and `PUBLIC`. Grant `authenticated` only what the app needs. Set `ALTER DEFAULT PRIVILEGES` so new objects are not granted to `anon`.
B. **profiles.** `authenticated` must not be able to change `role` or `id`: revoke UPDATE on the table and grant UPDATE only on `display_name` (or use a BEFORE UPDATE trigger that rejects the change). Remove INSERT on `profiles` for `authenticated`: rows are created only by `handle_new_user`. Role changes are made by the owner with SQL; document how.
C. **Policies and helper functions.** Recreate all policies `TO authenticated`, keeping both the owner and the teacher rules. Move `current_app_role`, `is_class_teacher` and `is_journal_teacher` into a schema `private` that is **not exposed** in the Data API. Make them SECURITY DEFINER with `set search_path = ''`. Grant EXECUTE on them to `authenticated` only and USAGE on the schema to `authenticated`: **do not revoke EXECUTE from `authenticated` on functions that policies call**, because policy expressions run with the caller's privileges and would break. Update the policies to use `private.*`, wrap calls as `(select ...)` to remove the init-plan warnings, then drop the old `public` functions.
D. **Other functions.** Pin `search_path` on every function (including `set_updated_at`). Revoke EXECUTE from `PUBLIC`, `anon` and `authenticated` on `handle_new_user()`; the Auth trigger keeps working. `save_lesson_record` stays executable by `authenticated` only and stays SECURITY INVOKER.
E. **v_lesson_window.** Keep `security_invoker = true`; no `anon` access.
F. **Migration file.** Forward-only: `supabase/migrations/<timestamp>_security_hardening.sql`. Do not edit already applied migrations.
G. **Tests.** Add `supabase/tests/security.sql` with the checks below.
